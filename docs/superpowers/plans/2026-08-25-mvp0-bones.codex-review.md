# CRITICAL

- **Tasks 2–4 — Concern:** The tasks cannot execute in order. Task 2 imports engine types created in Task 3; Task 3’s helpers import `setup.ts` and `apply.ts` from Tasks 4 and 9; Task 4 proposes an untyped temporary stub that violates `strict`/`noImplicitAny`. Tasks 3 and 4 also explicitly commit while tests remain red. **Change:** Move engine types before card ingestion, defer helpers until their dependencies exist, implement the real typed phase code before setup tests, and require the full current suite to be green before each commit.

- **Tasks 3 and 9 — Concern:** The supplied TypeScript does not typecheck. `helpers.ts` imports `PlayerId` from `state.ts`, which does not export it; `canonical(): string` returns `JSON.stringify(v)`, whose type includes `undefined`. **Change:** Import `PlayerId` from `types.ts`; handle `undefined` explicitly or restrict `canonical` to JSON values.

- **Tasks 4, 5, 7, 9, 10 — Concern:** The claimed final green suite is impossible as written. `DECK` contains 7–8 copies per code, so Task 4’s exact validation assertions and Task 9’s validated random walk fail; Task 5 expects turn 2 although the six-card hand creates a discard decision; Task 7 tries to cast a second non-generic `V-B1`; Task 9 expects non-acting players to have no commands although implementation returns `concede`; Task 10 expects an opponent deck count of 50 after five cards were dealt. **Change:** Use a genuinely valid 50-card fixture, resolve/avoid pending discard, use a distinct or generic Backup, align concession tests with §2.1, and assert the deck count from state (45 in that scenario).

# HIGH

- **Task 2, Step 8 — Concern:** The expected census is wrong. The official dump marks `1-121C`, `18-064C`, and `18-069C` with `multicard: "1"`, so the implementation produces `generic=3`, not `generic=0`. **Change:** Correct the expected census and add explicit assertions for all three generic cards.

- **Task 1 — Concern:** `pnpm lint` cannot work because no ESLint flat-config file is planned, and lint is never run during final verification. ESLint 9 expects an `eslint.config.*` configuration. **Change:** Add a TypeScript-aware flat config and include `pnpm lint` in every full verification run. [ESLint configuration files](https://eslint.org/docs/latest/use/configure/configuration-files)

- **Task 6, `enumeratePayments` — Concern:** Enumerating only source-minimal payments silently rejects legal CP generation. CR §11.2.2.3 permits generating arbitrary extra CP and discarding the unused CP; `apply` rejects every such non-minimal command because it is absent from `legalCommands`. **Change:** Enumerate all legal source selections within practical bounds, or separate “generated CP” from the exact CP selected for payment and validate semantically.

- **Task 7, `castCheck` — Concern:** Summons are incorrectly limited to Main Phases. CR §9.3.1.6 permits Summons during Main and Attack Phases, while the shared check rejects every Attack Phase cast. **Change:** Give Summons their own timing check and model the required Attack Phase action windows, or declare this broader restriction explicitly as an MVP0 simplification.

- **Tasks 5, 8, 9 — Concern:** `priority` is being used as “player who must make the next decision.” The defending player does not gain priority merely to declare a blocker; CR §10.1.2.6 and §10.1.3.6 instead give the turn player priority around those steps. This state shape will obstruct the planned stack/ability work. **Change:** Separate CR priority from pending decision ownership, e.g. `priority` plus `pending: { kind: 'declareBlock', player }`.

- **Task 3 state model / Tasks 9 and 13 — Concern:** The locked architecture’s event/command log, replay, and undo support are absent. `GameState` has no log, and `apply` stores neither commands nor events. **Change:** Add serialisable history now and test replay equivalence and undo-by-truncation, or explicitly defer and amend the spec.

- **Task 10, `viewFor` — Concern:** The view is not isolated from state. Hand arrays, field arrays, `FieldCard` objects, `attack`, `pending`, and `defs` are shared references; an adversarial Agent can mutate the engine through its supposedly filtered view. **Change:** Return cloned/frozen data or deeply readonly snapshots and add a mutation-isolation test.

- **Task 12, `selfPlay` — Concern:** The advertised fuzzer does not assert engine invariants. It only catches thrown errors and command-limit exhaustion; it does not check card conservation, unique zone membership, backup limits, hidden-view leakage, or input immutability. **Change:** Extract reusable invariant checks from Task 9 and run them after every self-play command.

- **Task 12, `hotseat` — Concern:** Hidden hands leak between players. The terminal retains the previous player’s rendered hand and immediately renders the next player’s view without a pass-device barrier. **Change:** Clear the screen and require confirmation whenever the acting player changes; avoid leaving hand contents in scrollback where practical.

# MEDIUM

- **Task 4, mulligan — Concern:** CR §8.2.1.4 lets the player order the five cards placed on the bottom. Keeping hand order removes a strategically meaningful choice without declaring it as a simplification. **Change:** Add an ordered mulligan command/decision, or mark and test the simplification explicitly.

- **Task 5, `finishEndPhase` — Concern:** It starts the next turn and draws before the central rule-process check runs. CR §9.5.1.4 requires rule processes after damage/effect cleanup and before the next turn. **Change:** Run the end-phase rule-process checkpoint before `startTurn`.

- **Task 8, `runRuleProcesses` — Concern:** CR §12.4.4 and §12.4.5 are conflated. A zero-power Character is put into the Break Zone, not broken; §12.4.5 applies the damage break process only at power 1000 or greater. The emitted `broken` event will later trigger the wrong abilities. **Change:** Model distinct zone-move reasons/events and implement the two thresholds separately.

- **Global constraints / Task 8 — Concern:** The plan first says First Strike is implemented, then explicitly ignores it and calls it deferred. There is no First Strike behavior or test. **Change:** Remove it from the implemented-keyword claim and mark the deferral consistently, or implement CR §15.2.3.

- **Task 9, command canonicalisation — Concern:** Array order is treated as significant for semantic sets. Reordered attackers, Backup sources, discards, or hand-size discards can be legally equivalent but are rejected before subsystem validation. **Change:** Canonicalise set-valued fields by ID or validate commands semantically rather than by serialized equality.

- **Tasks 4–9 — Concern:** The assertion that every `applyX` revalidates preconditions is false. `applyChooseFirst`, `applyMulligan`, `applyPass`, `applyDiscardToHandSize`, and `pay` rely heavily on the outer `apply` guard, yet all are planned as public exports. **Change:** Keep unchecked helpers private or add complete local validation.

- **Task 2 — Concern:** Card ingestion is not reproducible or defensive enough. - **Task 7, `applyCastSummon` — Concern:** It always emits `unimplementedAbility`, even when `hasAbilities` is false, contradicting the task’s stated event contract and the vanilla fixture. **Change:** Guard the event with `def.hasAbilities`, as Character casting does.

- **Task 12 package — Concern:** The `fftcg` bin points directly to a TypeScript file with no executable shebang; the package script works through `tsx`, but the advertised binary will not. **Change:** Provide a shebang wrapper invoking compiled JavaScript/tsx, or remove the bin entry.

- **Task 13, manual verification — Concern:** A randomly shuffled physical deck cannot match a Mulberry32-seeded engine shuffle merely by choosing the same seed. The CLI also does not expose or accept deck order. **Change:** Add explicit deck-order import/export or instruct the tester to arrange the physical deck from a printed seeded order.

- **Spec process / Task 13 — Concern:** The spec requires `HANDOFF.md` at each green commit, while the plan creates it only once at the end. **Change:** Add handoff updates to each task boundary or revise the spec’s process requirement.
